The predecessor

Industrial IoT Safety Monitoring System

Five sensors, soldered to fixed roles.

One ESP32, one gas sensor, one proximity sensor, one RFID reader — each wired to a role the firmware knew about by name. Each sensor got its own hardcoded Supabase table. Swapping the gas sensor for a soil-moisture probe meant reflashing the firmware and hand-adding a table before a single reading could land anywhere.

Nodeframe

A sensor is just a manifest now.

Every module carries a small plugin manifest — sensor chip, metric, unit, thresholds, dashboard widget — on its onboard EEPROM. The Core Hub reads it on connect and loads a driver. The backend is one generalized schema instead of one table per sensor type, so a new sensor type is a new row, not a new migration.

The mechanism

Three moves, no reboot.

What actually happens between seating a module in a slot and seeing its panel on the dashboard.

01

Module reports its manifest

On connect, the module's onboard EEPROM hands the hub a small manifest: sensor chip, metric key, unit, warning/critical thresholds, and which dashboard widget renders it.

02

Core Hub loads the driver

The hub matches the manifest to a driver, starts polling the slot, and writes rows into four generalized tables — not a bespoke schema per sensor.

plugins modules readings events
03

Dashboard renders itself

The dashboard reads the manifest's widget type and draws a panel for the new module automatically — no redeploy, no new frontend code.
